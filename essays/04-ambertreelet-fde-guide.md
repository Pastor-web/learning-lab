## 一、FDE 到底是做什么？

FDE 是 Forward Deployed Engineer 的缩写，通常译为「前线部署工程师」。

这里的「前线」指客户现场：FDE 进入客户的真实环境，理解业务、连接数据和系统，在现场快速构建应用，并把一线经验反馈给产品团队。

### 一个常见场景

公司想做 AI 客服，AI 能讲产品特点，也能找退换货政策，大家都很满意。一上线，问题来了。

用户问：「滑雪板能不能加钱发顺丰，明天到新疆？」AI 会算运费，却不知道滑雪板属于超长件；补上规则，又发现时效根本做不到。规则越补越多，回答也越长，用户还是不知道到底能不能买。商品、活动和售后政策又一直在变。谁更新资料，谁处理错答，项目开始时都没说清楚。

太麻烦了，大家又回到了原来的工作方式。

客户并不需要一个「万能 AI 客服」。**FDE 才是来处理真正业务的人**，在真实环境里，对一个可衡量的业务结果端到端负责。

### 一个完整过程

1. **需求识别**：去看一线员工平时怎样拿信息、完成任务、和同事协作，以及遇到例外时到底怎么处理。
2. **跨层沟通**：让管理层、业务负责人和一线员工达成一致；管理层投入资源，中层配合，一线也愿意交出真实流程和反馈。
3. **工程与系统集成**：处理数据、接入工具、编排 Agent、完成部署，接到企业原有系统；交付能稳定运行、经得起多人使用、可追溯的生产级能力。
4. **评估与验证**：项目开始前说清目标、测试任务、验证样本和验收标准，避免做完才发现双方理解不同。
5. **沉淀下来**：哪些规则可写成模板，哪些能力可做成 Skill，哪些问题该反馈给产品团队，避免项目结束就归零。

## 二、FDE 的具体分类：商务型、产品型、工程型

FDE 可以拆为三个可协作、也会重叠的方向：

### 商务型 FDE

更靠近客户和商业现场：寻找项目机会、识别真正能拍板的人、推动客户决策并维护合作关系。通常需要懂业务、懂组织、能建信任。销售、售前、客户成功背景更容易从这条路径切入。

### 产品型 FDE

更靠近问题和方案：把模糊表达拆成清楚需求，确定做什么/不做什么，设计方案、做 Demo，推动项目往前。产品经理、解决方案、项目经理和设计背景通常更有优势。

### 工程型 FDE

更靠近系统交付：把方案真正做出来——模型与数据、连接企业系统、测试部署、上线后稳定运行。研发、算法、测试和实施背景更适合从这里开始。

复杂项目较稳妥的最小组织，仍是商务、产品、工程组成的「铁三角」。

### Palantir 参考分工

- **Echo**：更靠近客户和业务现场，听懂客户、发现真问题，把模糊需求翻译成可执行方案；确定先做什么、做到什么程度、谁验收。
- **Delta**：更靠近工程和交付，快速原型、接数据与系统、测试与错误处理，保证能上线、能用、出问题知道怎么处理。
- **Solo FDE**：同时承担 Echo 和 Delta 的核心工作：既听得懂业务，也能把业务变成系统，并对最后结果负责。

## 三、第一个项目怎么开始

- **不要一上来就选大型客户**，量力而行，从熟悉行业里的中小企业切入。
- 先从自己熟悉的人和行业开始：亲友企业、原工作领域、垂直社群或已有客户关系。
- 不要一上来改造整家公司：先找一个具体的人、一项明确任务、一条能从头看到尾的流程，输入输出说得清楚。
- 选好以后，先亲自按原来的方式做一遍，再决定哪些环节适合交给 AI。
- 收集真实任务、常见样本和边界情况；提前约定什么叫「可用」、什么叫「失败」。
- 第一个项目别追求全自动：优先资料整理、客户跟单、初步分析等「出错也能人工复核」的环节。
- 找客户关键不是到处推销 AI，而是让相关人看到：你理解过类似问题，也有办法解决。

## 四、SOW、Spec、Demo、MVP：容易忽略的细节

### 名词

| 概念 | 含义 |
| --- | --- |
| **SOW** | 项目约定：做什么、谁负责、怎样算完成、临时加需求怎么办；给客户和项目负责人看 |
| **Spec** | 开发说明书：页面、数据、AI 步骤、测试场景；给开发团队看 |
| **Demo** | 演示样品：能跑的小版本，证明方向没错；重点是对齐理解 |
| **MVP** | 最小可用版本：可交给少量真实用户跑完一条完整工作流 |

### 注意事项

1. **什么项目不要接**：客户始终不愿让你接触真实流程、业务人员、数据样本或验收负责人——可能只是调研、比稿或内部汇报素材。
2. **信任优先**：用同行案例、可展示结果或行业经验换深入沟通，而不是一上来就要完整预算、数据和系统权限。
3. **进入现场看真问题**：谁发起、谁预算、谁验收；一线怎样获取信息、完成任务、处理例外；过去为什么一直没解决。
4. **验收标准必须写进 SOW**：目标、范围、交付物、双方责任、数据条件、里程碑、测试、验收、变更、付款节点。
5. **翻译成 Spec**：页面、数据来源、模型调用、可用资料、测试场景、上线节奏。
6. **先做最短 Demo 对齐方向**：一条核心流程 + 真实样本，证明对老板有价值、对业务可用、对 IT 可接入。
7. **正式交付**：接进真实工作；员工会用；出错有人处理；审批/付款/删除/对外发布要有人确认；敏感信息脱敏或私有环境。
8. **交付后留下能力**：稳定性、权限、异常、人工确认；规则、失败案例、测试方法、连接与模板沉淀。

## 五、Skill、CLI、Subagent、Hook：沉淀和复用

| 概念 | 通俗理解 |
| --- | --- |
| **Skill** | AI 的「岗位说明书 + 工作手册」：先看什么、按什么步骤、哪些红线、何时找人、交什么结果 |
| **CLI** | 打开企业系统的门：查 CRM、读订单、写回跟进 |
| **Subagent** | 分工小组：一个查资料、一个判断、一个检查 |
| **Hook** | 自动开关/报警：完成后通知、高风险人工确认、报错记录并通知 |

串起来的例子：

> Skill 告诉 AI 怎样判断线索 → CLI 查 CRM 和客户资料 → Subagent 分别处理查资料/判断/检查 → Hook 在完成、失败或高风险时自动通知相关人

Skill 的价值不在第一版，而在越用越好：新错误、新规则、新例外变成测试案例，再更新 Skill。多个客户反复遇到相似问题，共通部分整理成 Skill、CLI 和工作流——碎石路才会变成柏油路。

## 六、API、MCP、CLI 和 UI 自动化：企业系统怎么接？

**结论：** API 是系统本身的接口；MCP 和 CLI 是 Agent 调用能力的不同方式；UI 自动化是没有接口时的备用方案。

把 Agent 想成刚入职、需要和各部门协作的新员工：

- **API**：各系统的「直连办事窗口」
- **MCP**：「通讯录 + 办事指南」（有哪些工具、怎么填）
- **CLI**：「命令终端」（明确指令 → 结构化结果）
- **UI 自动化**：没有窗口时像人一样点屏幕；页面一变就容易错，放在最后

| 方式 | 何时用 |
| --- | --- |
| API | 系统有稳定接口；适合大量数据读写 |
| MCP | 希望 Agent 标准化发现和调用工具；工具别塞太多 |
| CLI | 本地开发、批处理、多工具组合 |
| UI 自动化 | 无 API、不能二开时救急，不当默认方案 |

## 七、传统测试不适合 Agent：EDD 循环六步走

### 名词

- **MVP 契约**：第一版 Agent 的工作边界（帮谁做什么、完成标准、不能做、能用什么、何时转人工）
- **EDD**：Evaluation-Driven Development，评测驱动开发——先做一点 → 真实案例测 → 找问题 → 改 → 再测
- **评测集**：正常题 + 信息不全 + 规则冲突 + 边界 + 历史失败
- **回归测试**：修完再跑旧题，防止改坏旧能力
- **LLM Judge**：另一个模型按标准初筛；高风险仍要人工
- **运行轨迹**：查了什么、调了什么、判断了什么、在哪失败

### 六步

1. 先写 **MVP 契约**
2. 准备 **真实测试题**（含四类：可直接答 / 需澄清 / 部分答 / 拒答或转人工）
3. 先定好 **谁来评分**（LLM Judge 可初筛，高风险人工终裁）
4. 先跑一遍，看第一版错在哪一层（资料 / 理解 / 工具 / 权限）
5. **优先改最重要的问题**
6. 修完把 **新旧题目全部再跑一遍**（回归）

这六步不断循环，Agent 才会慢慢变成「能稳定完成一段工作」。

## 八、辨别真假岗位，简历、作品集与面试

### 8.1 识别岗位

国内叫法不统一。别只看 Title，用五个问题问招聘方：

1. 薪资是不是主要靠签单提成？（是 → 更像销售/售前）
2. 工程实现占多少？（几乎不写代码、不接系统、不评测 → 难负责交付）
3. 项目结束后现场经验会留下什么？（留不下 → 更像一次性驻场）
4. 你是签约前演示，还是签约后还要继续负责？
5. 发现客户提错需求，你有没有权力说「不」？

能进现场、能做工程、能纠偏、还要对结果负责，才更像真正的 FDE。

### 8.2 简历：四个信号

1. 有没有从模糊问题一路负责到上线/验收/叫停
2. 有没有直接面对业务（访谈、澄清、推动决策）
3. 有没有进入真实环境（权限、出错、人工兜底）
4. 结果能不能说清楚（通过率、耗时、人工介入比例等）

写法：

> 有责任感的动词 + 你构建的东西 + 业务场景 + 可验证结果

例如：「协助客户搭建数据管道」→「为零售场景负责数据管道部署，整合多个分散数据源，并将业务分析准备周期从数周压缩到数天」

写了 Agent、RAG 或 MCP，就要能解释：为什么这样设计、数据从哪来、失败怎么处理、怎样证明可用。

### 8.3 作品集

招聘方想看：问题有多模糊 → 你怎么收住 → 遇到什么限制 → 有没有可验证结果。

一个完整项目写成交付故事：业务背景 → 需求边界 → 方案与取舍 → 交付过程 → 结果。

最好三种版本：

1. 项目长文（过程、判断、复盘）
2. GitHub README（架构、运行、评测、已知限制）
3. 一页 PDF（背景、职责、方案、结果、链接）

脱敏：客户名改成「华东某制造企业」等；金额、账号、订单、聊天用模拟数据；截图遮姓名、联系方式、内部域名。

没有企业客户时：亲友小店、同事重复工作、社群运营、自己的工作流——只要真有人用、有反馈、有迭代，就比纯展示 Demo 更像 FDE 作品集。

### 8.4 面试

常见模糊题：「这里有 8000 条出租车运营记录，一周内做一个方案。」

你应先问：谁是用户？最痛的问题？一周最值得验证哪项价值？这次不做什么？成功标准？数据能不能拿？谁验收？

这就是 **Scoping**：把大问题收成有限时间可验证的小闭环。

面试官主要想看：先澄清再动手；能切分可验证部分；想到脏数据/老系统/权限/接口失败/人工兜底；能说出假设；有取舍；压力下仍讲清楚；一直想着真正使用的人。

日常准备：每周一个模糊需求，两分钟讲清用户、目标、边界、风险、成功指标；准备几段真实行为故事（扛责任、失败、取舍、说服）。

## 最后

把观猹这套内容看完，我对 FDE 的理解变了。其实每一步都不轻松。

要能判断什么项目值得做，什么需求只是客户一句「我们也想要 AI」；要知道哪些能力该沉淀成 Skill，哪些操作必须交给人确认；也要接受：Demo 做出来只是开始，能稳定交付、能不断迭代，才是更难的部分。

所以，FDE 不是一个靠背术语就能进入的岗位。

它不躲在需求文档后面，也不止步于演示页面；进入真实现场，理解真实限制，对最后的结果负责。

**FDE 最终交付的也不是一个 Agent，而是一段已经跑起来、有人愿意持续使用的业务流程。**
